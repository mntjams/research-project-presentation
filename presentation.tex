\section{Introduction}
\begin{frame}
    \frametitle{ELMM}
    \begin{itemize}
        \item Extended Large Eddy Microscale Model (ELMM) is a Large Eddy Simulation (LES) model for atmospheric flows\pause
        \item Written in Fortran\pause
        \item Parallelized using OpenMP, MPI, or hybrid MPI + OpenMP\pause
        \note {
            - Porting this code to GPUs could greatly benefit its performance
        }
        \item In each time step a \alert{Poisson equation} must be solved
    \end{itemize}
    \begin{block}{Poisson equation}
        The Poisson equation is
        \[
            \Delta \phi = b
        \]
        \begin{itemize}
            \item pressure change $\phi$
            \item net outflow of predicted wind $b$
        \end{itemize}
    \end{block}
\end{frame}

\begin{frame}
    \frametitle{PoisFFT - Poisson solver}
    \begin{itemize}
        \item Library that solves the Poisson equation\pause
        \item Determined to be the best starting point for ELMM performance improvement\pause
        \note{
            - It is a self-contained library
            - Takes up noticable portion of the run-time
        }
        \item Solves the equation using an FFT-based method\pause
        \item Parallelized the same way as ELMM
        \note {
            - While measuring the performance, we encountered several hybrid configurations where PoisFFT straight up segfaulted
            - See next slide for configuration definition
            - With no existing documentation and PFFTs (PoisFFT multi-node FFT library) hybrid option being in development for the past 10 years, we gave up on that
        }
    \end{itemize}
\end{frame}

\begin{frame}
    \frametitle{Outside view of PoisFFT}
    \begin{itemize}
        \item User defines a domain:\pause
            \begin{itemize}
                \item dimensionality,
                \item number of grid cells,
                \item grid lengths, and
                \item boundary conditions (BCs)\pause
            \end{itemize}
        \item Then (repeatedly) solves the equation by supplying $b$
        \note{
            - $b$ is just an array of size (ns_x, ns_y, ns_z)
            - Both $b$ and $\phi$ can be surrounded by ghost cells
        }
    \end{itemize}
\end{frame}

\begin{frame}
    \frametitle{Inside view of PoisFFT}
    PoisFFT has two phases:\pause
    \begin{enumerate}
        \item \alert{initialization}, and\pause
            \begin{itemize}
                \item Precompute the normalization factor and eigenvalues,
                \item prepare FFT plan (or plans), and\
                \item allocate workspaces\pause
            \end{itemize}
        \item (repeated) \alert{execution}\pause
            \begin{itemize}
                \item Apply forward FFT,
                \item divide every element by a sum of pre-computed eigenvalues,
                \item apply backward FFT, and
                \item normalize the result
                \note {
                    - The steps differ a bit depending on the configuration
                }
            \end{itemize}
    \end{enumerate}
\end{frame}

\begin{frame}
    \frametitle{Inside view of PoisFFT}
    \begin{itemize}
        \item It became apparent that despite the initially simple outline, this will not be easy...\pause
        \item PoisFFT has \alert{no documentation} and only limited usage guide, is sparsely commented with poor code hygiene\pause
        \note {
            - D is a solver
            - D1D is a 1D solver, but we never use it to solve anything, it is used to just hold data
            - tmp1, tmp2, ctmp1, ctmp2
        }
        \item The architecture is not ideal
        \note {
            - It is entirely possible to create a solver without an error but the solver does nothing on each Execute
            - They are interleaved with ifdefs to form if-else blocks based on compile time definitions
        }
    \end{itemize}
\end{frame}

\section{poisson-solver}
\begin{frame}
    \frametitle{poisson-solver — a modern PoisFFT port}
    \begin{alertblock}{Our goal}
        Create a PoisFFT GPU port with better performance and better software architecture\pause
    \end{alertblock}
    How to achieve that?\pause
    \begin{enumerate}
        \item Move the hot path to a GPU,\pause
        \item replace relevant libraries with GPU-based alternatives,\pause
        \item improve separation of concerns of individual parts, and\pause
        \item write documentation for the solver
    \end{enumerate}
\end{frame}

\begin{frame}
    \frametitle{The architecture of poisson-solver}
    \begin{itemize}
        \item poisson-solver makes a clear distinction between:\pause
        \begin{itemize}
            \item configuration-based decisions,
            \item implications of those decisions, and
            \item compile-time setup\pause
        \end{itemize}
    \end{itemize}
    \begin{block}{Solver plan}
        A configuration-dependant plan that the rest of the solver follows.
        Includes: the solve method, strategies for eigenvalue computation, reshape types, etc.
        \note {
            - Reshapes are used in MPI code to get one axis into a local memory
            - Reshape types are e.g. (to pencil, to slab)
        }
    \end{block}\pause
    \begin{block}{Solver core}
        Owns objects, buffers and precomputed values specified by the plan.
        E.g., precomputed eigenvalues, FFT plan, the reshaper or, device workspaces.
        \note {
            - FFT libraries usually work by first defining a plan which optimizes for the specified FFT usage
            - Then, repeatedly executing such plan
        }
    \end{block}
\end{frame}

\begin{frame}
    \frametitle{The architecture of poisson-solver}
    \begin{block}{FFT policies}
        Policies describing how to perform the FFTs depending on the build type.
        One is purely local, the other also works in distributed environments.
        \note {
            - Different libraries are used for different build types
        }
    \end{block}\pause
    \begin{block}{Reshaper}
        Certain steps of the execution pipeline require data locality.
        A reshaper object performs transitions between decompositions.
        \note {
            - The decompositions and transitions between them are precomputed during the solver core construction
        }
    \end{block}
\end{frame}

\begin{frame}
    \frametitle{GPU-based FFT libraries}
    \begin{itemize}
        \item CPU-based libraries offer a diverse support of DFTs\pause
        \item GPU-based alternatives often lack such diverse support\pause
        \item We found a single-node GPU FFT library\pause
        \item We didn't found a distributed library with the required support...\pause
        \item So we chose one and extended it!
        \note {
            - The authors have opened pull request on their repo
        }
    \end{itemize}
\end{frame}

\section{Performance}
\begin{frame}
    \frametitle{What did we measure?}
    \begin{itemize}
        \item PoisFFT \pause vs poisson-solver (with host-device copies) \pause vs poisson-solver (with only device-device copies)
    \end{itemize}
\end{frame}

\begin{frame}
    \frametitle{Local results}
    \begin{itemize}
        \item poisson-solver (only device-device copies) always wins!\pause
        \begin{itemize}
            \item 2.4x to 10.4x speedups (25th to 75th percentile)\pause
            \item Maximum speedup is 113x\pause
        \end{itemize}
        \item poisson-solver (with host-device copies) wins in $\sim 60\%$ of cases\pause
        \begin{itemize}
            \item 0.75x to 1.80x speedups (25th to 75th percentile)
        \end{itemize}
    \end{itemize}
\end{frame}

        \end{itemize}
        \item poisson-solver (with host-device copies) also always wins!\pause
        \begin{itemize}
            \item 1.31x to 2.36x speedups (25th to 75th percentile)
        \end{itemize}
    \end{itemize}
\end{frame}

\section{Conclusion}
\begin{frame}
    \frametitle{Achievements}
    \begin{itemize}
        \item Ported and modernized a Poisson solver library\pause
        \item Significantly improved software architecture\pause
        \item Performance improvement for:\pause
            \begin{itemize}
                \item all setups with buffers already on a GPU,\pause
                \item most of local setups when copy is inevitable,\pause
                \item all distributed setups
            \end{itemize}
    \end{itemize}
\end{frame}

\begin{frame}
    \frametitle{Future work}
    \begin{itemize}
        \item Port more of ELMM onto a GPU\pause
        \item Don't do it by hand\pause
        \item Develop a system that compiles Fortran source code into C++/CUDA source code, handles buffer copying, etc.
    \end{itemize}
\end{frame}

\begin{frame}
    \frametitle{Computational fluid dynamics}
    \begin{block}{Navier-Stokes equations}
        The Navier-Stokes equations are
        \[
            \rho (\frac{\delta \mathbf{u}}{\delta t} + \mathbf{u} \cdot \nabla \mathbf{u}) = -\nabla p + \mu\nabla^2 \mathbf{u} + F
        \]
        \begin{itemize}
            \item fluid density $\rho$
            \item velocity vector field $\mathbf{u}$
            \item time $t$
            \item pressure field $p$
            \item dynamic viscosity $\mu$
            \item external forces $F$
        \end{itemize}
    \end{block}
